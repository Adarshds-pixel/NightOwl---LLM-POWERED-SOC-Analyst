**2026-08-16 — pySigma used for rule validation only; NightOwl's own engine does per-event evaluation (Day 7 detection engine v1).**
- **What we evaluated:** whether `pysigma` (the official Sigma rule library) could handle both parsing *and* evaluating rules against a live event, end to end.
- **What we found:** pySigma's design centers on *backends* — converters that turn a parsed rule into a target query language (Elasticsearch DSL, Splunk SPL, etc.) to run against an external log store. There's no official backend for evaluating a rule against a single in-memory Python object, which is exactly what `POST /ingest` needs (one normalized event, evaluated in-process, no external SIEM in this stack).
- **Decision:** use `pysigma`'s `SigmaRule.from_yaml()` at load time for real structural validation (catches malformed rules with proper error messages — a genuine, non-decorative use of the library), then evaluate with a small hand-rolled interpreter (`app/detection/engine.py`) over the rule's `detection` block, loaded separately via `yaml.safe_load`. The evaluator supports the common subset of Sigma semantics: named selections (AND across fields, OR across a value list), `contains`/`startswith`/`endswith` field modifiers, and a boolean `condition` string (`and`/`or`/`not`/parentheses) via a small recursive-descent parser — not `eval()`, since rule files are treated as untrusted input.
- **Known v1 limitations (by design, not oversight):** no `|re` or glob-wildcard modifiers, no `1 of`/`all of` condition shorthand, no named multi-condition rules. Easy to extend later if a specific rule needs it.
- **Reversible?** Yes — `rule_loader.py`/`engine.py` are the only files that know about this; a future move to a full pySigma backend (e.g. if the project adds a real SIEM/Elasticsearch target) wouldn't change any caller.

**2026-08-16 — Detection rules match against real Sysmon field names (Image, CommandLine, DestinationIp, ...), not NightOwl's normalized event schema.**
- **Alternatives considered:** writing rules against the normalized schema's own field names (`process`, `command_line`, ...) to keep the detection engine fully decoupled from Sysmon's raw XML shape.
- **Why real Sysmon names instead:** rules become portable from public Sigma/SigmaHQ sources — a stronger, more credible claim for the project than an invented vocabulary, and immediately recognizable to anyone familiar with real SOC tooling.
- **How the coupling risk was avoided:** `normalizer.py` already computes a flattened `{FieldName: value}` dict from each record's `EventData` before mapping the 3 fields it promotes to columns. `NormalizedEvent` now also carries that full dict as `event_data` (`schemas/event.py`), so `engine.py` gets every Sysmon field for free — not just the 3 the normalizer promotes — without re-parsing XML itself. The engine matches against the union of `event_data` and the normalized fields, so both vocabularies work.
- **Reversible?** Yes — `event_data` is additive; nothing that read `NormalizedEvent` before Day 7 is affected.

**2026-08-18 — `Alert.severity` is a direct pass-through of the matched rule's `level` string (Day 8 alert persistence).**
- **Alternatives considered:** a fixed severity enum (`low`/`medium`/`high`/`critical`) with an explicit `level -> severity` translation table, in case rule authors ever use non-standard level strings.
- **Why pass-through instead:** `Alert.severity` is a plain `String(50)` with no DB-level constraint, and every rule file's `level` already comes from Sigma's own small standard vocabulary (`informational`/`low`/`medium`/`high`/`critical`). A translation table would just map each string to itself — added indirection with no behavior difference.
- **Decision:** `services/detection_service.py`'s `create_alert` sets `severity = match.level` directly.
- **Reversible?** Yes — confined to one line in `create_alert`; if a real enum constraint is added to the `alerts` table later, only this function needs to change.
- **Update (2026-08-19, Day 10):** `match.level` is no longer the raw, unweighted Sigma rule level — `engine.evaluate_event` now runs it through `severity_service.compute_severity()` before building the `RuleMatch` (see the Day 10 entry below), so this pass-through decision still holds, but what's being passed through changed meaning.

**2026-08-19 — Registry-based detection scoped to Sysmon Event ID 13 (Value Set) only (Day 9, 10 rules total).**

**2026-08-19 — Severity scoring combines base Sigma level + MITRE tactic weight, both derived from each rule's own `tags:` list (Day 10).**
- **What we needed:** "combine rule severity + technique tactic weight" per the roadmap, so e.g. a "medium" rule tagged `command_and_control` ranks above a "medium" rule tagged only `reconnaissance`.
- **Where the tactic comes from:** rule authors already tag rules with both a technique id (`attack.t1547.001`) and tactic name(s) (`attack.persistence`) — Day 9's `rule_loader.py` change parses both out of the plain `tags:` list (not from pySigma's parsed object model, consistent with how `condition`/`detections` are already parsed from the raw YAML dict). This is tag *extraction*, not MITRE-dataset validation — validating tag values against the real ATT&CK dataset stays Day 11's job (`mitre/validator.py`).
- **Formula:** `services/severity_service.py`'s `compute_severity(base_level, tactics)` — base rank 1-5 (informational..critical) plus the *highest* weight among the rule's tactics (0 for recon/resource-dev, +1 for initial-access/execution/persistence/priv-esc/defense-evasion, +2 for credential-access/discovery/lateral-movement/collection, +3 for command-and-control/exfiltration/impact), capped at critical. Tactic *tag spelling* matches this project's existing convention (underscores, e.g. `command_and_control`, not MITRE's site hyphens) since that's what the Day 7/8 seed rules already use.
- **Where it's applied:** `engine.evaluate_event` calls this when building each `RuleMatch`, so `RuleMatch.level` (and therefore `Alert.severity`) is always the final weighted value, not the raw rule level. Confirmed live: the Day 7 seed rule (`level: high`, tagged `attack.execution`) now produces `severity: critical` alerts (high=4 + execution weight 1 = 5), a visible, intentional behavior change from Day 8.
- **Reversible?** Yes — the weight table and formula are isolated in one function; existing tests/rules with no tactics see zero behavior change (weight 0), which is why no Day 7/8 test needed updating for this.

**2026-08-18 — Unknown/deprecated/revoked MITRE technique tags are warn-only, not rule-rejecting (Day 11).**
- **What we needed:** `mitre/validator.py` (Pair 2's Day 6 scaffold) deliberately left the acceptance policy for invalid technique ids to Pair 1 — its docstring says so explicitly, since the scaffold itself already keeps deprecated/revoked techniques in the lookup rather than dropping them.

The Day 11 roadmap row's own Files column only lists `detection/rules/*.yml`, `mitre/validator.py`, `services/incident_service.py` (not `models/rule.py`), and no roadmap day currently reads from the `rules` table either — the closest consumer is Pair 2's Day 16 rules-manager UI (`api/routes_rules.py`, enable/disable), which is a future day for the other pair. **2026-08-19 — Unhandled exceptions get one shared JSON 500 handler instead of per-route try/except (Day 12).**
- **What we needed:** "consistent API error handling across routes." The existing routes already raise `HTTPException` consistently (FastAPI's default handler turns that into `{"detail": ...}` JSON already) — the actual gap was the *unhandled* case: Starlette's built-in fallback for an uncaught exception returns plain text, not JSON, breaking every route's response contract the one time it matters most (a real bug).

**2026-08-19 — LLM call robustness: explicit provider timeout, a dedicated 503 for LLMProviderError, and an opt-in response cache (Day 12).**
- **What we needed:** the roadmap's Day 12 row asks to "handle LLM API timeouts, rate limits, malformed responses gracefully" and to "cache responses during repeated testing" against free-tier rate limits. Before this, `llm_client.get_llm_client()` set no request timeout on either provider client (a hung call could block indefinitely — not actually "handling" a timeout, just retrying after the fact), and `LLMProviderError` was never caught anywhere in the route layer — it fell through to `core/errors.py`'s generic `Exception` handler, returning an unhelpful `"internal server error"` 500 that's indistinguishable from an actual bug.
- **Timeout:** new `settings.llm_timeout_seconds` (default `30.0`), passed to both provider constructors. Confirmed via each provider's Pydantic model fields that the kwarg name differs: `ChatGoogleGenerativeAI` takes `timeout`, but `ChatGroq` takes `request_timeout` — passing the wrong name for Groq would have silently done nothing (extra kwargs aren't validated away, they just wouldn't reach the actual timeout behavior), so this was checked directly against the installed package versions rather than assumed from the Gemini side.
- **503 handling:** `core/errors.py`'s `install_exception_handlers()` now also registers `@app.exception_handler(LLMProviderError)` → `503` with the exception's own (already descriptive) message as `detail`, registered ahead of the generic handler. `LLMProviderError` is imported *inside* the function rather than at module scope — `core/errors.py` has no other imports from `app/rag`/`app/services`/etc. and stays a leaf module; the local import mirrors `rag/explain_service.py`'s existing pattern of importing a sibling module's symbol inside the one function that needs it. Starlette dispatches by nearest-matching exception type, so this required no route-level changes — it covers both `/explain` and `/chat` automatically.
- **Cache:** `llm_client._response_cache`, a module-level dict keyed on a SHA-256 hash of the exact rendered message contents, gated behind `settings.llm_cache_enabled` (default `False`). Off by default because this is a testing aid for burning through a tight free-tier daily quota during repeated manual runs, not production behavior — a real incident's explanation shouldn't silently go stale because an earlier identical-looking call was cached. Only a *successful* call is ever cached (populated after `_generate_raw` returns, never in the retry/failure path), so a transient provider error can't get "stuck" as a cached failure.
- **Reversible?** Yes — the timeout/cache are both additive `Settings` fields with safe defaults, and the 503 handler is one more `@app.exception_handler` registration; removing any of the three reverts to prior behavior with no other call-site changes.

**2026-08-19 — Token usage/latency measurement is a separate `generate_with_metrics()`, not a change to `generate()`'s contract (Day 12).**
- **What we needed:** "measure token usage and response time per explanation, document" (`docs/llm-cost-latency.md`). The raw LangChain response carries `.usage_metadata` (input/output/total tokens) on real Gemini/Groq calls, but `generate()` already returns just `str` and every existing caller (`explain_service.py`, `chat_service.py`) and its whole test suite (`tests/rag/test_llm_client.py`) depends on that.
- **Decision:** extracted the existing retry loop into a private `_generate_raw(messages) -> tuple[response, str]`; `generate()` becomes a thin wrapper unwrapping the text (behaviorally identical, zero existing test changes needed). Added `generate_with_metrics(messages) -> GenerationMetrics` (`text`, `input_tokens`, `output_tokens`, `total_tokens`, `latency_seconds`, `provider`, `model`) for measurement use only — `explain_service.py`/`chat_service.py` keep calling plain `generate()`. `generate_with_metrics` deliberately bypasses the Day 12 response cache (a cache hit's near-zero latency/near-zero tokens would defeat the point of measuring a real call) and reads `usage_metadata` via `getattr(..., None)`, falling back to `None` fields rather than raising when absent (e.g. against a mocked response in tests, or a provider/version that doesn't populate it).
- **New `backend/scripts/llm_cost_latency_check.py`:** unlike Day 10's `hallucination_spot_check.py`, this doesn't need the real ingest/Postgres pipeline — it's purely measuring the RAG explain call, so it uses 5 crafted incident dicts directly (same precedent as the `if __name__ == "__main__"` blocks already in `rag/explain_service.py`/`rag/llm_client.py`) against the real, already-built Chroma knowledge base (no server process — `PersistentClient` reads `data/chroma/` directly) and a real LLM call per case (draft + critique, mirroring `generate_explanation`'s actual two-call shape). 5 incidents × 2 calls = 10 requests, chosen to leave headroom under Gemini's 20 req/day free-tier cap. See `docs/llm-cost-latency.md` for the results and methodology in full.

**2026-08-21 — Two separate LLM response caches, and a fixed "system" actor for the audit log until real user identity exists (Day 13, Pair 2).**
- **Why a second cache, distinct from Day 12's `llm_client._response_cache`:** the roadmap's Day 13 row asks to "cache `explain()`/`chat()` results keyed on incident id (+ message, for chat)," closing a gap this doc already flagged at Day 8/11 but never implemented. That's a different cache from Day 12's: this one is **on by default** (production behavior protecting the free-tier quota, not a manual-testing toggle), keyed on the **caller-facing incident id** rather than the exact rendered prompt, and sits one layer up in `rag/cache.py` — wired in at the route call site around `explain_service.generate_explanation`/`chat_service.generate_chat_reply` — so a hit skips the retriever call too, not just the LLM call. Both caches coexist without conflict; `rag/cache.py`'s module docstring cross-references `llm_client.py`'s to make the split explicit for the next reader.
- **Wired at the route, not the service function:** `explain_service.py`/`chat_service.py`'s function signatures are unchanged. Existing route tests (`tests/api/test_incidents_route.py`, `tests/api/test_chat_route.py`) monkeypatch `generate_explanation`/`generate_chat_reply` directly with fakes matching today's exact call signature (e.g. `def fake_generate_chat_reply(incident, history, message)`); changing those signatures to thread an `incident_id` through would have broken every one of those fakes. Checking the cache in the route (`routes_incidents.py::explain_incident`, `routes_chat.py::chat_with_incident`) before calling the service keeps the service layer untouched.
- **TTL, not permanent:** `settings.response_cache_ttl_seconds` (default 900s) — an incident's status/context can change (e.g. via the new `PATCH /status`), so an explanation shouldn't be cached forever.
- **Test isolation gotcha:** the cache's dicts live for the whole pytest process, but every test's `api_client` fixture gets a *fresh* in-memory SQLite DB whose autoincrement incident ids restart at 1 — so a cached result from one test file could otherwise leak into an unrelated test reusing the same id. Fixed with an autouse `_clear_response_cache` fixture in `tests/conftest.py`.
- **Audit log "actor" defaults to a fixed `"system"` string:** there is no user/auth model anywhere in this codebase yet — Pair 1's Day 13 API key auth (parallel work, not covered here) is a single shared secret header, not per-user identity. `POST /explain` and `POST /chat` have no natural place for a caller to supply an actor, so both always record `actor="system"`. The new `PATCH /incidents/{id}/status` endpoint (added specifically so there's a status change for the audit log to record — no such endpoint existed before Day 13) accepts an optional `actor` field in its body for forward compatibility, still defaulting to `"system"` when omitted. Revisit once a real per-user identity concept lands.
- **Reversible?** Yes — `rag/cache.py`, `models/audit_log.py`, and `services/audit_service.py` are all new, additive files; the route changes are each a conditional cache check/audit call wrapped around existing logic, and the new endpoints are additive routes. Rolling back the alembic migration (`eb2982ae8841`) drops the `audit_log` table cleanly.

**2026-08-19 — A broken Windows temp-directory ACL is worked around in `tests/conftest.py`, not fixed at the OS level (found during Day 12 full-suite verification).**
- **What we needed:** running the full suite (`pytest -v`) to verify Day 12 surfaced 8 errors in Pair 1's `tests/detection/test_rule_loader.py`, all `PermissionError: [WinError 5] Access is denied` on `%LOCALAPPDATA%\Temp\pytest-of-<user>` — pytest's own `tmp_path` fixture failing at *setup*, before any test code runs, for every test that uses it. `icacls`/`Get-Acl` on that folder both also failed with "Access is denied", even for the folder's own owning account — a real fix (`takeown`/`icacls /grant`) needs an elevated shell, which this sandboxed dev environment doesn't have. This wasn't present at Day 11's last full-suite verification (`181 passed, 0 failures`), so something in this machine's temp-directory ACLs changed between sessions — not a Day 12 regression, but blocking a clean "all green" result for the milestone sign-off.
- **Decision:** `tests/conftest.py` gained a `pytest_configure(config)` hook that tries to list the default `pytest-of-<user>` directory; on any `OSError` (and only if the caller hasn't already passed `--basetemp` explicitly), it redirects pytest's `--basetemp` to a fresh sibling directory (`<tempdir>/nightowl-pytest-tmp`) instead. This sidesteps the broken directory entirely rather than requiring elevation, and is a no-op on any machine where the default already works (including CI, or a teammate's machine that's never hit this).
- **Alternatives considered:** a `pytest.ini` `addopts = --basetemp=...` line — rejected because `pytest.ini`'s parser doesn't expand environment variables (confirmed: `${TEMP}` was passed through literally, not resolved, so this doesn't work portably across machines/users without hardcoding a path). The `conftest.py` hook computes the path in Python instead, so it works for whoever runs the suite next regardless of username.
- **The underlying OS-level ACL problem is still unresolved** — this only stops the test suite from depending on that specific broken directory being readable. Left as a known machine-level quirk, not something worth chasing further for a student project's dev environment.
- **Reversible?** Yes — the hook only changes `config.option.basetemp` when it detects the specific failure mode; deleting it reverts to pytest's default behavior everywhere.
